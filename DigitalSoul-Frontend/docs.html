DigitalSoul Documentation

Complete engineering reference for compiling consented desktop and browser telemetry into deterministic DAG workflows, running via browser-use Actor sessions with strict cryptographic approval gates.

System Overview

DigitalSoul bridges the gap between probabilistic AI observation and deterministic mission-critical automation. While language models excel at synthesizing intent, executing critical tasks across enterprise systems demands mathematical determinism and zero hallucination risk.

Guiding Architectural Principles

  • Deterministic DAG Execution: Workflows compile to strictly typed Directed Acyclic Graphs with AST-compiled expressions and invariant checks.
  • Decoupled Observation & Execution: Extension telemetry is strictly sandboxed with PII and credential sanitization at source.
  • CDP Native Browser Control: Automations use browser-use 0.13.11 connecting directly via Chrome DevTools Protocol, preserving authentic browser state without synthetic Playwright shims.
  • Agent-Side Safety Gates: State-mutating actions (R2) require verified cryptographic effect hashes (SHA-256) matching operator approvals before firing.

M1 – M4 Architecture

DigitalSoul is partitioned into four decoupled modules coordinated through formal contracts:

Module Domain Key Technologies & Capabilities
M1 Learning & Observation Engine Consented DOM telemetry, semantic action observer, credential redaction at source, workflow pattern mining.
M2 Deterministic Execution Backend FastAPI local host (127.0.0.1:7777), browser-use CDP driver, SQLite WAL idempotency, Ed25519 pairing, RFC 8785 canonicalization.
M3 Operator Frontend & Control Live telemetry visualization, interactive approval review modals, dry-run simulation dashboard.
M4 Shared Bus & Application Integration Acme demo adapters, persistent shared event sink, audit logging, enterprise SSO gateway.

browser-use CDP Driver

DigitalSoul explicitly standardizes on browser-use 0.13.11 using its BrowserSession, CDP, and Actor APIs. Playwright imports and emulated drivers are strictly prohibited.

Why browser-use? Traditional automation frameworks rely on brittle synthetic events that fail under modern bot-mitigation, canvas rendering, or complex Web Component shadows. browser-use communicates directly with Chrome DevTools Protocol to inspect genuine DOM layouts and monitor network correlation.

Dedicated Profile & Browser Discovery

The driver isolates state under .ghost/chrome and automatically detects installed Windows Chrome or Microsoft Edge binaries. To override the target browser executable:

PowerShell
$env:DIGITALSOUL_BROWSER_EXECUTABLE = "C:\Program Files\Google\Chrome\Application\chrome.exe"

OmniRoute Local AI Gateway

OmniRoute serves as our high-performance local inference proxy, running on loopback at http://127.0.0.1:20128/v1. It wraps models with unified OpenAI-compatible completions and ensures credentials never leave the host.

PowerShell
# Verify OmniRoute gateway health and list configured models Invoke-RestMethod -Method Get -Uri 'http://127.0.0.1:20128/v1/models'

Safety, Approvals & Risk Levels

DigitalSoul categorizes all step operations into distinct risk tiers to ensure irreversible external side effects cannot be executed autonomously.

Tier Description Execution Policy
R0 Internal AST evaluations, DAG computations, string interpolations. Automatic execution.
R1 External read-only actions (DOM query, GET request, status check). Automatic execution with verification receipt.
R2 State mutations (Form submission, POST/PATCH, file write). Halt for operator approval; requires SHA-256 effect hash match.
R3 Destructive external operations (account deletion, database wipe). Blocked by default by policy engine.

Cryptographic Effect Binding

When an R2 step is encountered, DigitalSoul generates an authoritative preview and calculates an RFC 8785 canonical JSON hash of the action payload (effect_hash). When an operator approves the action via POST /api/v1/runs/{id}/approve, the approval is strictly bound to this exact hash:

JSON Approval Payload
{ "approval_id": "appr_9823f401", "workflow_version": 4, "step_id": "step_tag_churn_risk", "effect_hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855" }

REST API Reference

All endpoints are served from http://127.0.0.1:7777. Requests require Authorization: Bearer <token> and strict Host/Origin verification.

Method Path Description
POST /api/v1/workflows/{id}/runs Trigger workflow run with parameters and mode (dry_run or supervised).
GET /api/v1/runs List recent workflow runs with status filtering.
GET /api/v1/runs/{id} Retrieve authoritative run state, checkpoints, outcomes, and pending approvals.
POST /api/v1/runs/{id}/approve Submit signed approval for an awaiting R2 step.
POST /api/v1/runs/{id}/reject Reject step mutation and cancel execution.
POST /api/v1/safety/stop Latches emergency stop killswitch and cancels all nonterminal tasks.

Blinky Technical Reference Notes

Blinky (C:\Projects\Blinky) served as our prior technical benchmark for desktop telemetry and action correlation. Key evolutions in DigitalSoul include:

  • From Coordinate Clicks to CDP Actors: DigitalSoul eliminates brittle (x, y) coordinate clicking in favor of semantic DOM locators and browser-use CDP Actor adapters.
  • Deterministic Approval Binding: Rather than granting generic run-level authorization, DigitalSoul enforces per-iteration SHA-256 effect hash matching.
  • Windows DPAPI Credential Isolation: Local session tokens are encrypted via Windows Data Protection API (DPAPI) rather than plaintext configuration stores.
